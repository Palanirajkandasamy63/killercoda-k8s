Storage
that outlives the Pod

Volumes, PersistentVolumeClaims, PersistentVolumes and StorageClasses — and the three places on that path where a Pod stops before it runs.

The failure lands on the Pod: Pending, no logs. kubectl get pvc reads the claim, and the claim says why.

What you'll walk away with

  • The volume abstraction — a directory the containers in a Pod can reach, provided by .spec.volumes and placed by volumeMounts
  • The claim and the volume — a PVC requests storage, a PV is the storage, a StorageClass provisions one to satisfy the other, and a claimRef binds them
  • The get pvc triage — one command splits a storage-stuck Pod three ways: the claim is absent, Pending, or Bound and refused
  • Provisioning and binding — dynamic against static, Immediate against WaitForFirstConsumer, and when a claim may grow
  • Access modes and reclaim policy — what RWO, ROX, RWX and RWOP each permit, and what delete pvc destroys

One chain, four objects,
a scope change partway through

Kubernetes separates asking for storage from supplying it. Trace the chain top to bottom.

StorageClass
the recipe

A named recipe: which provisioner, which parameters, which reclaim policy, which binding mode.

→
PersistentVolume
provisioned to match — cluster-scoped

A piece of storage in the cluster that an administrator provisioned, or that the class provisioned dynamically.

→
PersistentVolumeClaim
binds via claimRef — namespaced

A request for storage by a user: a size, an access mode, optionally a class.

→
Pod
names it: claimName

Names only the claim, and only one in its own namespace. The Pod stays disposable; the claim is the durable handle to its data.

A volume is a directory

At its core, a volume is a directory, possibly with data in it, that the containers in a Pod can reach. The volume's type decides what backs it, how long it lives, and which nodes reach it.

# two declarations, joined by name spec: volumes: # what to provide - name: data persistentVolumeClaim: { claimName: cdr-data } - name: scratch emptyDir: {} containers: - name: app volumeMounts: # where to put it - { name: data, mountPath: /data } - { name: scratch, mountPath: /tmp/work }
  • Both halves are required. A provided-but-unmounted volume does nothing.
  • A mount naming no volume is invalid.
  • Two containers mounting one volume at different paths share one directory.

The binding is one claimRef,
read from either side

The volume's claimRef names the claim. The claim's volumeName names the volume, one-to-one.

# PersistentVolume — points down at the claim spec: capacity: { storage: 20Gi } claimRef: namespace: cdr-storage name: cdr-data # binds to this PVC # PersistentVolumeClaim — points up at the volume spec: volumeName: pv-cdr-a3f91 # binds to this PV resources: requests: { storage: 20Gi }
  • Binding is exclusive: a bound volume refuses every other claim, however well it matches.
  • A deleted claim leaves a stale claimRef — a Released volume never rebinds on its own.
  • kubectl get pv reads the same bind in its CLAIM column.

Where the volume comes from

Dynamic provisioning

When no static volume matches, the claim's StorageClass provisions one for it, sized and configured to fit. No administrator in the loop.

whenthe default path

Static provisioning

An administrator creates volumes in advance. A claim binds to a pre-existing one that matches on size, access mode and class.

whenpre-provisioned pools
  • A storageClassName that does not exist: no provisioner answers, no volume appears, claim stays Pending.
  • describe pvc names it: storageclass ... not found.
  • Omitting storageClassName takes the cluster default.
  • storageClassName: "" disables dynamic provisioning. It binds only to a pre-created classless volume.

When a claim binds,
and when it may grow

Both settings live on the StorageClass, not on the claim.

Immediate

Binds as soon as the claim is created, wherever the volume happens to land. The default when a class omits the field.

bindsat claim creation

WaitForFirstConsumer

Delays binding until a Pod uses the claim, so the volume lands on that Pod's node. Set by most node-local classes.

bindswhen a Pod consumes it
  • A WaitForFirstConsumer claim with no consumer shows Pending, which is healthy. Event: waiting for first consumer to be created before binding.
  • Broken only once a Pod wants it and it still will not bind.
  • Growth needs allowVolumeExpansion: true on the class. Absent by default.
  • Raising the claim's storage request expands the volume. Growth is one-way only.

Access modes count nodes,
except one that counts Pods

ModeShortWhat the volume permits
ReadWriteOnceRWOread-write by a single node; Pods on that node all share it
ReadOnlyManyROXread-only by many nodes
ReadWriteManyRWXread-write by many nodes
ReadWriteOncePodRWOPread-write by a single Pod, cluster-wide
  • RWO permits many Pods, as long as they share one node.
  • RWOP refuses a second Pod even on the same node.
  • A volume mounts under one access mode at a time, even when it supports several.

A volume reports its lifecycle
as a phase

PhaseMeaning
Availablea free resource, not bound to a claim
Boundthe volume is bound to a claim
Releasedthe claim is deleted; the cluster has not yet reclaimed the storage
Failedautomatic reclamation failed
  • A claim's phase is simpler: Pending, Bound, or rarely Lost if its bound volume disappears.
  • Failed is the one to escalate. The driver could not delete the backing storage, so the API object may misrepresent infrastructure that still costs money.

What a delete destroys

Two mechanisms decide the outcome when a claim is deleted.

Delete

Destroys the volume object and the storage behind it. The data is gone. The default on most dynamic classes.

use forscratch data

Retain

Keeps the volume and its data, moving it to Released for a human to recover.

use fordata whose loss is an incident

Recycle

Deprecated. Use dynamic provisioning instead.

use fornothing new
  • Storage Object in Use Protection: blocks removal of a claim any Pod still references.
  • A kubernetes.io/pvc-protection finalizer holds it in Terminating until the consumer is gone. A delete that appears to hang is usually that finalizer working.

One storage path, three places it stops

A different object owns each hop. Read the claim first. The Pod's status only says it is stuck.

kubectl get pvc is the first look

The claim's STATUS column splits every storage-stuck Pod, before you reach for Pod logs that do not exist yet.

# always the first command on a storage-stuck Pod kubectl get pvc -n cdr-storage NAME STATUS VOLUME CAPACITY ACCESS MODES STORAGECLASS cdr-data Bound pvc-9f2a 1Gi RWO local-path # a Pod stuck Pending — the claim it names is not in that list kubectl describe pod cdr-writer-0 -n cdr-storage persistentvolumeclaim "cdr-dat" not found
  • Bound: the volume delivered storage, but refuses this Pod.
  • Pending: the claim cannot get a volume.
  • Absent from the list: a claimName typo, or a claim in another namespace.

A Bound claim can still strand a Pod

Attach makes a volume available to a node, then mount exposes it in the container. Attach is where the access mode bites. One claim, several replicas: the first Pod's node attaches it exclusively.

A second node

  • Asks for the same RWO volume, and cannot have it.
  • The Pod hangs while the claim still reads Bound.
block volumeMulti-Attach error
local volumedidn't match PersistentVolume's node affinity

A second Pod

  • Asks for an RWOP volume, even on the node already using it.
  • The scheduler refuses to place it.
scheduler... ReadWriteOncePod access mode
  • None of these is a broken volume. Each access mode keeps its promise.
  • Fix: one consumer where the mode allows only one, RWX on network storage, or volumeClaimTemplates for one claim per replica.

What to carry forward

  • The volume abstraction — a directory the containers in a Pod can reach. .spec.volumes provides it, volumeMounts places it. Most types die with the Pod; only a claim reaches storage with its own lifecycle.
  • The claim, the volume, the class — a claim requests storage, a volume is the storage, a StorageClass provisions one to satisfy the other. The binding is exclusive and one-to-one, and a Pod names only the claim, in its own namespace.
  • The get pvc triage — one command splits every storage-stuck Pod three ways: the claim is absent, Pending, or Bound while the Pod is still stuck. Not every Pending is broken.
  • Access modes — RWO gives one node many Pods, RWX gives many nodes, RWOP gives exactly one Pod.
  • Reclaim policy — reclaimPolicy: Delete makes kubectl delete pvc a data-destruction command. In-use protection is the only thing that slows it down.
